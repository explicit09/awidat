ASSISTANT:
Yes! "Coding harness" usually refers to the scaffolding around an LLM that turns it into a working coding agent — the loop, tools, prompts, and context-management that sit between the model and the actual codebase.

The main pieces are usually:

- **The agent loop** — read user request → think → call a tool → observe result → repeat until done. Most harnesses are some variant of this.
- **Tool surface** — what the model can actually do. Typically file ops (read/write/edit), shell execution, search/grep, and sometimes browser or LSP access. The choice and design of tools matters a lot; e.g. a targeted `Edit` tool that does exact string replacement tends to outperform "rewrite the whole file" because it forces the model to ground its changes in what's actually there.
- **Context management** — the codebase doesn't fit in the window, so the harness has to decide what to load. Strategies include lazy reading (only open files the model asks for), retrieval/grep-first workflows, and subagents that go off, do a bounded task, and return a summary instead of polluting the parent's context.
- **System prompt / instructions** — conventions about formatting, when to ask vs. act, how to use tools, style of output. This is where a lot of the "personality" and reliability comes from.
- **Verification** — running tests, type-checks, or linters in the loop so the model gets real feedback rather than just guessing whether its change worked.
- **Permissioning / safety** — gating destructive actions (deletes, network calls, force pushes) behind user confirmation.

Claude Code, Cursor's agent mode, Aider, SWE-agent, OpenHands, and Devin are all different points in this design space — same basic loop, very different tool sets and context strategies.
