# Plan-set verification verdict

**OK to action as-is:** False

## Summary
The plan set is well-grounded in the real codebase — file paths, the YouTube adapter traits, the FSM, the token/XOR stub, the SQLite schema, the desktop stub commands, and the LOCAL_USER_ID actor were all verified to exist as described, and the dependency numbering forms an acyclic DAG. However it is NOT ready to action as-is because of one load-bearing cross-phase contradiction and several unowned artifacts. The decisive issue is the sync-vs-async store/API seam: Phase 1 forks a parallel async SocialStore trait + async SocialApi driver, while Phases 2/3/4/6/7 all add methods to the synchronous SocialStore and call the synchronous SocialApi/UploadService directly from the server (Phase 3 even pins the FSM as sync with a leaf block_on). These cannot both be true; resolve the server execution model first. Secondary blockers: workspace_member_roles is defined with two incompatible schemas (Phase 1 payload_json vs Phase 7 flat role column); the Supabase Storage signed-URL file-transport that Phases 3/5/6 all consume is owned by no phase; the YouTube quota counter Phase 3 enforces references a Phase-1 table Phase 1 never creates; axum is declared default-features=false so the Phase-1 server won't serve without added features; and Phase 5's config plumbing targets a per-field config struct in commands/config.rs that does not exist (config lives in awidat_config::Config). Fix the async decision, assign single owners for the storage/quota/roles artifacts, and tighten the Phase 2->3 hard ordering, then the set is actionable.

## Cross-phase issues
- SYNC-vs-ASYNC STORE SEAM is the single biggest cross-phase contradiction. The existing `SocialStore` trait (crates/social/src/store.rs:22-105) is fully synchronous, and `SocialApi` (crates/social/src/api.rs) is built on it. Phase 1 Step 3 decides to add a NEW parallel `async` trait (`AsyncSocialStore`) plus a 'thin async SocialApi driver' for the Postgres/server path. But Phases 2, 3, 4, 6, and 7 all describe adding store methods to 'SocialStore' and driving 'SocialApi' methods directly on the server with no mention of the async fork: Phase 2 Step 3 adds `set_connected_account_status` to `SocialStore`; Phase 3 Step 6 calls `SocialApi::execute_claimed_upload_job` server-side; Phase 4 Steps 3-4 add `processing_publish_jobs`/`accounts_with_expiring_tokens` to `SocialStore` and call `PublishService::claim_due_jobs`+`SocialApi` from axum handlers; Phase 7 Step 3 adds a by-user role query to the store. If Phase 1 actually forks into a second async trait + async API, then every store method those later phases add must be implemented TWICE (sync + async) and SocialApi must exist in two forms — none of those phases budget for that. Conversely Phase 3 Step 3 explicitly keeps the FSM/UploadService SYNCHRONOUS and bridges async at the leaf client with block_on, which contradicts Phase 1's 'async SocialApi driver'. The set is internally inconsistent about whether the server runs sync-on-blocking-pool or a parallel async stack; this must be resolved before any coding.
- TOKEN-ENCRYPTION KEY-PROVIDER TRAIT contract is changed by Phase 2 in a way that ripples but is under-acknowledged. Phase 2 Step 1 repurposes `LocalTokenKeyProvider` to require exactly-32-byte keys and ChaCha20-Poly1305. `account_service.rs:51-80` (`complete_oauth`) and the desktop `key_provider()` (commands/social.rs:49) both depend on this trait. Phase 1 deploys the server in Phase 1 with the OLD XOR token model and the existing `TestKeyProvider`; Phase 2 then swaps the crypto. That is sequenced OK, but Phase 3's production `AccessTokenResolver` (Phase 3 Step 5) calls `decrypt_access_token(&key_provider)` and Phase 4's `TokenRefresher` re-encrypts via `TokenSecret::encrypt` — both assume the Phase-2 AEAD key shape. If Phase 3 server-wiring lands before Phase 2 (Phase 3 even offers a 'decrypt-only, no refresh' fallback), the deployed server would be doing AEAD-or-XOR depending on merge order. Pin Phase 2 strictly before any Phase 3 server wiring (Phase 3 already flags this as a hard dependency, but its own depends_on lists [1,2] while offering a code path that runs without Phase 2 merged).
- SCHEMA OWNERSHIP / workspace_member_roles overlap: Phase 1 Step 1 creates all eight tables including `workspace_member_roles` mirroring the SQLite shape `(workspace_id TEXT, user_id TEXT, payload_json TEXT, PK(workspace_id,user_id))` (verified at sqlite_store.rs:111-117). Phase 7 Step 3 then says it will 'add/confirm a workspace_member_roles table' with a DIFFERENT shape `(workspace_id text, user_id text, role text)` plus RLS. Two phases own the same table with two different column designs (payload_json blob vs a flat `role` column). The existing `WorkspaceMemberRole` serde model is persisted as payload_json in SQLite; Phase 7's flat `role` column would break the serde round-trip Phase 1 deliberately preserves. Must reconcile to one schema.
- QUOTA-COUNTER ownership is split without a defined source of truth. Phase 3 Step 6 enforces the YouTube 100/day cap in the server worker, counting either a Postgres counter row 'from Phase 1' OR counting `Uploaded` events in publish_job_events. Phase 1's schema (verified) creates NO such counter table, and there is no `Uploaded` PublishJobEventType guaranteed. Phase 4 Step (open risks) also references the cap but defers. No phase actually owns creating the quota-counter schema/migration; Phase 3 assumes Phase 1 produced it, which Phase 1 did not.
- FILE-TRANSPORT (Supabase Storage signed URL) is assumed by Phases 3, 5, and 6 but no phase definitively OWNS standing up the Storage bucket + the signed-URL handshake endpoint. Phase 5 lists it as a [USER] prerequisite 'decided in Phase 1', but Phase 1's plan never mentions Supabase Storage or an upload-URL endpoint at all (Phase 1 only does Postgres + service skeleton + mock adapters). Phase 3's `ArtifactSource` and Phase 6's PULL_FROM_URL/`video_url` both need a server-reachable signed URL that nothing creates. This is a missing artifact a later phase assumes an earlier one produced.

## Ordering problems
- depends_on DAG is acyclic and mostly sane: 1<-2<-3<-4; 5 depends [1,2,3,4]; 6 depends [1,2,3,4]; 7 depends [1,2,5]. No phase depends on a strictly later phase number. However: Phase 3 depends_on [1,2] but ships a server `AccessTokenResolver` that needs Phase 2's refresh entrypoint; Phase 3 itself offers a decrypt-only fallback if Phase 2 isn't merged — meaning Phase 3 server-wiring can technically run before Phase 2's refresh exists, producing a deployed server that 401s on expired tokens. The dependency should be a HARD ordering (Phase 2 fully merged before Phase 3 server wiring), not the soft 'or ship a TODO' the plan allows.
- Phase 4 depends_on [1,2,3] and assumes a deployed reachable server with a Postgres SocialStore. That is consistent, but Phase 4 Step 5's pg_cron schedule firing real jobs implicitly requires Phase 3's real adapter AND Phase 2's refresh AND the file-transport/signed-URL (unowned) to be live; the cron 'fires jobs through the service' but artifact resolution (ArtifactSource/signed URL) has no owning phase before Phase 4, so a Phase-4 end-to-end fire could not resolve real video bytes.
- Phase 1 starts the cron template DISABLED and only proves a manual pg_net smoke test; Phase 4 enables the real schedule. Good. But Phase 1 ALSO deploys `/internal/tick` that calls `claim_due_publish_jobs` + `execute_claimed_upload_job` against the MOCK adapter. If Phase 1's manual smoke test or any accidental cron enablement runs against the mock, it could transition real-looking jobs through a mock publish before Phases 2-4 land. Phase 1 flags keeping cron disabled, but the ordering relies on operational discipline, not a code guard.
- Phase 7 depends_on [1,2,5] but NOT on [3,4]. That is defensible (auth is orthogonal to firing), yet Phase 7's HTTP middleware (Step 4) protects the same `/internal/*` worker routes that Phase 4 creates, and Phase 7 says worker entry points stay protected by 'the cron secret from Phase 4'. So Phase 7 implicitly depends on Phase 4's internal-auth scheme existing; the depends_on omits 4.

## Per-phase gaps
- Phase 1: The `axum` workspace dependency is declared `default-features = false` (Cargo.toml:422). A functioning HTTP server needs the `http1`/`tokio` server features; Phase 1 Step 6 says 'mount Axum routes' but never adds the required axum features, so `crates/social-server` as described will not bind/serve. Flag and fix the feature set.
- Phase 1: Step 3 claims the workspace `sqlx` 'features list sqlite not postgres; add postgres'. Verified (Cargo.toml:504-513 has sqlite but NOT postgres). The plan is correct that postgres must be added, but note adding `postgres` alongside `sqlite` to the SAME workspace sqlx entry pulls postgres into every crate that uses workspace sqlx — acceptable but should be called out; the alternative (crate-local sqlx) is mentioned but the plan leaves the choice open, which is a real unresolved decision affecting compile surface.
- Phase 1: claims it mirrors the SQLite schema 'row-for-row, same column names'. Verified the actual SQLite tables are payload_json-blob-heavy with only a few denormalized columns (e.g. connected_accounts = id, owner_json, provider, provider_account_id, status, payload_json, updated_at — sqlite_store.rs:41-50). The plan's prose listing per-column types (TEXT->text, INTEGER epoch->bigint) is broadly right, but it must mirror the denormalized+payload_json hybrid exactly, not invent fully-normalized columns. The plan mostly says this but the 'eight tables row-for-row' phrasing risks an over-normalized Postgres schema that breaks serde parity.
- Phase 2: Step 2 resolves channel identity via YouTube `channels?part=id&mine=true`, but `oauth_url.rs:48` requests ONLY `https://www.googleapis.com/auth/youtube.upload`. Phase 2's own risk flags this, but the plan text in Step 2 asserts it will 'fill provider_account_id' without committing to ADD the read scope to `scopes_for(YouTube)` — a concrete edit to oauth_url.rs that the plan should mandate, not leave to a risk note. As written the exchange would fail `complete_oauth`'s consistency check.
- Phase 2: Step 4.2/4.3 — the server-side OAuth callback handler is described as landing 'in the Phase-1 service module', but Phase 1 only stands up OAuth start/complete STUBS and explicitly defers real OAuth to Phase 2. The desktop `social_oauth_complete` stub (commands/social.rs:145-190, verified fabricating stub-access/stub-refresh) removal is conditioned on Phase 5; Phase 2 leaves a feature-flagged stub that 'may never be exercised end-to-end until both phases land' — an untested real path, self-flagged but unresolved.
- Phase 3: Step 6 says 'replace the mock adapter mounted in the server', referencing Phase 1 mounting MockUploadAdapter. Verified the YouTube traits (youtube_upload.rs:35-72: `YouTubeUploadClient::upload_video`, `YouTubeStatusClient::poll_status`) and adapters already exist with error mapping at :216-228. Phase 3's reuse claim is accurate. Gap: Phase 3 introduces `force_private` and chunk-size config on the client, but the existing `YouTubeUploadAdapter`/request types (UploadPrivacy already normalized) have no `force_private` field — adding it touches the tested adapter, mildly contradicting 'only the concrete client impl is missing'.
- Phase 4: Step 2 claims `upload_service.rs` arms call `upload_in_progress.fail(...)` at 'lines 195-233' and that `MediaConstraintFailed` is an arm. Verified `fail(` appears at upload_service.rs:196 and :218 — the line refs are approximately right. But Phase 4 proposes threading `max_attempts`/`base_backoff_secs` into `ExecuteUploadInput` (verified struct at upload_service.rs:10-19 has NO such fields) and `ExecuteUploadRequest` in api.rs — a real signature change to a tested struct that every caller (including the desktop mock path) must update; the plan under-scopes the blast radius of changing `ExecuteUploadInput`.
- Phase 4: Step 4 depends on a server crate 'created in Phase 1' with axum + a Postgres-backed SocialStore, but per the sync/async contradiction above, whether the worker can call the synchronous `PublishService::claim_due_jobs`/`SocialApi` against a Postgres store is unresolved. Phase 4 assumes a synchronous-callable Postgres store, which directly conflicts with Phase 1's async-trait decision.
- Phase 5: Step 1 claims it will add a SocialServerConfig 'to the persisted config struct and its getter/setter command, following the existing config field pattern in config.rs'. Verified commands/config.rs (lines 6-142) has NO such per-field config struct — it operates on `awidat_config::Config` loaded from project_root and only exposes indexer-config commands. There is no desktop-app-level mutable config struct to extend in that file as described; the plan's 'follow the existing field pattern' is based on a pattern that does not exist there. Config plumbing must target awidat_config::Config or a new mechanism.
- Phase 5: Step 6 'grep client_secret in live path' and gating legacy publishing/ behind a feature — verified the legacy path is real and extensive (apps/desktop/src-tauri/src/publishing/ has oauth_exchange.rs, oauth_listener.rs (loopback 127.0.0.1:8419), keychain.rs, youtube_upload.rs, tiktok.rs, instagram.rs). Feature-gating a directory that is wired into commands/publishing.rs and AwidatState.upload_queue (state.rs:105) is a larger refactor than the plan implies (the render-queue auto-upload tests render-queue-upload.test.ts, upload-metadata.test.ts depend on it).
- Phase 6: Step 1/Task 3 — `reqwest` is NOT a dependency of crates/social (verified Cargo.toml has only base64/serde/serde_json/rusqlite/sha2/thiserror). Phase 6 correctly says live clients belong in the server crate, but the existence/shape of that server crate is entirely dependent on Phase 1's unbuilt `crates/social-server`, and Phase 3 is also assumed to have placed the live YouTube client there. Phase 6 explicitly flags it cannot confirm where Phase 3 put the client — a real unresolved dependency.
- Phase 7: Step 1 adds `auth_context.rs` to the 'dependency-light' crates/social, but Step 2's `supabase_jwt.rs` needs a JWT lib + reqwest for JWKS — the plan correctly proposes feature-gating or placing it in the server crate, but again the server crate's existence/identity is unconfirmed (Phase 1 names it `crates/social-server`; Phase 4/6/7 hedge with 'wherever Phase 1 put it'). Consistent naming is missing across phases.
- Phase 7: Step 6 deletes `LOCAL_USER_ID` and `actor()/owner()` from commands/social.rs (verified at :37-45). But Phase 5 already rewrote commands/social.rs bodies to call the SERVER (deleting with_store, oauth_complete, execute_upload). Phase 7 depends_on [1,2,5] but its Step 6 edits assume the Phase-5 end state of social.rs, which Phase 5 may have already removed the local-actor path from — the two phases edit the same file with overlapping assumptions about its post-Phase-5 shape (Phase 7's own risk acknowledges 'need to confirm Phase 5's actual end state').
